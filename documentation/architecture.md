# SafeRoute architecture

## System overview

```text
React 18 + TypeScript + Vite (port 3000)
  ├── Leaflet + OpenStreetMap tiles
  ├── relative /api requests ── Vite proxy ── Flask REST API (port 5000)
  └── optional MetaMask connection indicator (Ethers.js)
                                            ├── SQLite: users, fleet, trips, telemetry,
                                            │            incident reports, transaction metadata
                                            ├── local scikit-learn pipelines (joblib files)
                                            ├── off-chain canonical JSON evidence + SHA-256
                                            └── Web3.py → Hardhat JSON-RPC → SafeRouteRegistry.sol
                                                     (port 8545, chain 31337)

Python simulator ─┐
                  ├── POST /api/sensor-data → validated and provenance-labelled telemetry
ESP32 + GPS + IMU ┘
```

The React frontend, Flask API, local Hardhat chain, and physical device are independent processes. Vite proxies relative `/api` URLs; the UI does not bake internal `127.0.0.1` service addresses into browser requests. Start Hardhat, deploy the Solidity contract, then start Flask and the frontend. A chain outage disables on-chain writes but leaves local records usable with an explicit unanchored/unavailable status.

## Main data flow

1. An operator account is authenticated with a hashed password; API requests use a bearer token. New registrations are operators; administrator routes require the seeded/admin role.
2. A vehicle record is created in SQLite. If the deployed contract is reachable, Flask computes a stable bytes32 identity from the application vehicle ID, calls `registerVehicle`, waits for its receipt and stores transaction metadata. Otherwise the SQLite record stays local-only.
3. Trip creation validates that the vehicle exists and has no active trip. With chain availability, Flask ensures the vehicle exists on-chain, then calls `registerTrip` and `startTrip` separately. Each returned receipt is persisted; partial outcomes are indicated rather than collapsed into success.
4. Simulator, browser demo action, or ESP32 submits a validated payload. `source` must be `simulation` or `device`; coordinates/speeds and sensor fields are range checked. The three local classifiers run in process.
5. SafeRoute creates a checkpoint ID and a canonical JSON evidence object containing sensor data and model outputs, stores that report off-chain and computes SHA-256. A linked active trip can receive a contract checkpoint record with scaled coordinates and digest. A failed/unavailable transaction creates no transaction row.
6. An emergency flag or accident model output creates an incident ID/report with AI assessment and sensor evidence. SafeRoute hashes the report off-chain and attempts a compact on-chain incident record if a known contract trip ID is linked.
7. Incident verification hashes the exact stored evidence bytes again. A report is `modified` if the bytes do not match the stored digest; it is `verified` only if integrity matches and the contract's `verifyIncidentHash` returns true; an unavailable or absent on-chain record stays `not_anchored` or `chain_mismatch`.
8. Trip completion updates SQLite and writes a separate contract completion transaction when the chain lifecycle is valid.

## Provenance and trust boundaries

- `simulation`: generated by SafeRoute UI action or `iot/simulate.py`; never a measured bus/sensor reading.
- `device`: a firmware client declared its source; it is not independent proof of calibration, mounting, GPS quality, or the honesty of the sender.
- AI outputs: local scikit-learn inference with `synthetic_training_data` provenance; classifier output is not a decision, diagnosis, or real-world performance guarantee.
- on-chain: shown only after a transaction receipt from configured Hardhat RPC. A saved SQLite row by itself is not on-chain.
- evidence: full canonical report bytes stay in the local evidence folder, not on-chain. The chain stores compact IDs, lifecycle metadata, coordinates and digests. The hash detects changes relative to the original digest, but does not prove who produced the sensor input or whether that input was accurate.
- MetaMask: the shell can request an account and display its address/chain. Prototype writes still use Flask's unlocked Hardhat development account; they are not MetaMask-signed.

## Persistence and lifecycle

SQLite schema and seed rows are implemented in `backend/database.py`. Seed values are clearly simulation-labelled and the seed function does not create blockchain transaction rows. `backend/evidence/` contains off-chain evidence files and `backend/deployment.json` describes the current local contract address/chain; both are local runtime artifacts and ignored by Git. Model weights and measured synthetic evaluation metadata live in `ai_models/models/`. Hardhat build/cache files and Vite output are regenerated locally.

## Prototype security boundary

Use only on a controlled development machine/private LAN. The prototype bearer token is not an identity provider; protect/rotate the JWT secret, use production auth/authorization, TLS, validated device identity, key custody, backups and explicit evidence retention before considering deployment. Do not expose the ESP32 API or local Hardhat endpoint to the public Internet. Use synthetic data only.
